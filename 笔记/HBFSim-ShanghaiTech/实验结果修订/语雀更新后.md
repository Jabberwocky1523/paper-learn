# HBFSim（上科大）
**论文：** HBFSim：真实 GPU 执行下高带宽闪存的快速、忠实模拟

**版本：** 上科大参与的这篇，本地原文标注 arXiv:2609.09800v3，2026 年 9 月 30 日。

在真实 GPU 上运行 LLM，通过 PTX 插桩把指定访存交给 HBF 模型计时，并把温度、刷新和容量不足带来的影响加回这次执行。

## 一、背景动机
### 1. HBF 的机会与核心问题
+ **容量压力：** 权重和 KV 缓存都要占用显存。HBF 希望用 NAND 的高密度提供更大的容量，同时通过大量并行访问提供较高读取带宽。
+ **适合的数据：** 模型权重基本只读，跨请求共享的前缀 KV 缓存也有多读少写的特点，比较适合 NAND。每步更新的活跃数据仍然需要快速、耐写的存储空间。
+ **带宽高不等于延迟低：** 带宽是持续搬运数据的速率，延迟是一次访问需要等待的时间。很多平面同时工作可以提高总带宽，但不能直接消除每次 NAND 读取本身的等待。
+ **本文的参数：** 背景部分以约 20 μs 的 HBF 页读取和约 200 ns 的 GPU 全局访存作说明，约差两个数量级。FlashAccel 采用了另一套器件假设，不能直接沿用它的 4 μs 参数。
+ **提前读取的机会：** 作者估算 H100 上计算第 i 层可为下一层权重留下约 130.2 μs 的提前量，是假设页读延迟的约 6.5 倍。这个数字说明存在重叠机会；是否真正覆盖延迟，还要看传输量、带宽、缓存空间及专家路由何时确定。[原文第 2 节，PDF 第 2–3 页]

### 2. 之前模拟方法的局限
+ **硬件还不可用：** 本文研究时没有可用于验证的真实 HBF 芯片。作者要解决的是，怎样在硬件问世前，先判断放置策略、容量比例和温度等因素对真实 LLM 执行的影响。
+ **cycle-level模拟太慢：** cycle-level模拟器需要模拟大量 GPU 指令,并且速度较慢。LLM 推理的指令量很大，完整运行一次的代价很高。
+ **固定轨迹限制探索：** 一份轨迹记录的是某个配置下发生过的操作。改变 HBM/HBF 比例后，框架可能调整常驻张量、KV 分配和迁移操作，这些变化无法由原轨迹自动产生。重新采集轨迹是可能的，但就不能只靠同一份静态轨迹快速比较所有配置。
+ **作者的选择：** 计算、内核执行和可重叠的工作由真实 GPU 完成，模拟器主要补上 HBF 对程序可见的服务影响.

### 3. 真实 GPU 上模拟 HBF 的三个难点
+ **在哪里拦截：** 假设 HBF 位于加速器封装内，GPU 的访存不必经过主机块设备队列。只修改 SSD 驱动，无法捕获这种访问，所以作者选择对 GPU 内核的 PTX 插桩。
+ **在哪里等待：** GPU 发出读取后，可以继续执行不依赖返回值的指令。如果一发出读取就让线程停下来，会破坏这部分重叠，把 HBF 的影响算得过大。
+ **温度,数据保持,读干扰这些NAND特性都会影响模拟精度：** 前面的请求会影响排队，温度会影响服务速率，数据保持和读干扰会触发刷新。只给每次读取加一个固定延迟，无法描述这些长期影响。

## 二、设计方案
### 1. 改进机会
+ **真实执行然后在PTX访存拦截：** LLM 仍然在真实 GPU 上运行，HBFSim 通过重写 PTX 捕获声明范围内的访存，再加入 HBF 服务延迟。这样可以保留真实计算，也能观察改变容量配置后程序实际产生的行为。
+ **在使用数据的位置等待：** 将访存发出和数据消费分开。发出时登记请求，等后续指令真正需要数据时再等待，尽可能保留访存与计算的重叠。
+ **温度、刷新和访存建模：** 请求产生热量，温度影响服务速率和数据保持期限，刷新又与应用争用介质，最后把新增等待反馈到正在运行的程序。
+ **支持超过物理显存的逻辑容量：** 用有限的显存页框缓存和主机后备文件保存数据，使工作负载能访问更大的逻辑地址范围，并校验换入换出后的数据内容。

+ D1 识别地址，D2 保留异步。
+ D3 计算热反馈，D4 处理保持和刷新。
+ D5 扩展容量，D6 尝试预取。其中预取尚未接入详细时序路径。

### 3. 工作流程
1. **地址注册与 PTX 改写：**应用在主机端显式注册 HBF 地址区间及访问属性，由运行时将地址范围信息发布到设备侧。PTX Pass 对可支持的 GPU 访存指令进行改写，插入 HBFSim 辅助逻辑，使设备端能够在实际执行时判断访问属于 HBM 还是 HBF。同时生成包含原始与改写代码哈希、辅助函数 ABI 和指令覆盖信息的准入记录，对未满足覆盖要求的 Kernel 拒绝执行。
2. **发出并分类：** GPU 执行到访存时检查实际地址。未注册部分走原生路径；有效 HBF 部分登记请求，交给HBF的模拟器服务。
3. **服务并反馈：** HBF模拟器结合排队、当前热状态和刷新计划处理请求，将完成结果写回原请求的完成槽。访问活动同时送入能耗和热模型，更新后续服务状态。
4. **执行：** 不依赖这份数据的指令可以继续；真正需要这份数据时，检查对应完成对象。所需完成条件全部满足后，GPU 继续后续计算。 

### 4. D1：明确哪些地址属于 HBF
+ **注册区域：** 应用把一段虚拟地址区间登记为 HBF timing or capacity range。每个range包含起始地址、长度、权限、页几何、关联流和后备文件偏移等信息。
+ **按实际地址判断：** 不能只看某条指令是不是读取，因为同一条指令在不同执行中可能访问不同数据。实际执行相关指令的时候会检查有效地址,按照实际地址来判断属于哪一层.
+ **TMA 需要具体拆分：** TensorMap 是主机生成的 128 B 描述符，包含基地址、维度、步长和数据块形状等。HBFSim 记录它的内容和版本，发出时枚举有效元素地址，将一个数据块拆为 HBM、HBF 和越界部分分别处理。
+ **有些cubin里面存在访存指令但是不便于改写：** 已经编译好的 cubin 没有可改写的 PTX，当前方法不能自动观察其中每次访存。运行时必须检查相关执行文件里面的代码被改写完，否则拒绝启动并记录原因。

### 5. D2：发出访问后先继续，使用数据时再等
+ **GPU 原本的行为：** 读取指令发出后，硬件用scoreboard记录哪个寄存器的结果还没回来。后续不使用这个寄存器的指令可以继续执行；第一次真正使用该结果时，如果数据还没到，才需要停下来。
+ **具体做法：** 发出时创建一个设备端完成对象device future，记录这次访问的模拟完成信息，然后继续执行。第一次依赖它的指令到来时，再查询或等待该对象。
+ **TMA 完成条件：** TMA 本身是异步搬运，不同指令可以在它工作时继续执行。HBFSim 用barrier、CTA、cluster和version对象，要求“原生 TMA 已完成”和“模拟 HBF 服务已完成”同时成立后，才算完成TMA。

### 6. D3：根据访问产生的热量，更新服务速率
**① 从访问活动算能量。** 每个读、编程和擦除事件都有能量，基本形式为：

$ E_{\mathrm{NAND}}=E_{\mathrm{command}}+e_{\mathrm{byte}}\times N_{\mathrm{bytes}} $

命令有固定成本，搬运字节也有成本。事件能量按 10 ms 时间窗累计；跨越多个时间窗的事件按重叠时长分配，不能把全部能量算到某一个瞬间。

$ P_{i,k}=\frac{E_{i,k}}{\Delta t}+P_{\mathrm{idle},i} $

也就是用“这一段时间的能量÷时长”得到活动功率，再加空闲功率。

**② 整个封装一起算温度。** GPU、HBM 和 HBF 放进同一个热网络，热量可以互相传递。离散后的节点关系为：

$ C_i\frac{dT_i}{dt}=P_i-\sum_jG_{ij}(T_i-T_j)-G_{i,\mathrm{sink}}(T_i-T_{\mathrm{sink}}) $

+ **左边：** 节点储热造成温度变化，热容越大，同样净热量下升温越慢。
+ **右边第一项：** 节点自己发出的热。
+ **右边后两项：** 与相邻节点、散热端交换的热；温差和热导决定传热量。
+ **耦合的意思：** 即使 HBF 自己的功耗没变，附近计算芯片更热，也可能使 HBF 更热。因此不能只给每种介质单独算一个温度再取平均。

**③ 用降阶模型支持在线更新。** 先离线用 3D-ICE 构建全阶模型，向各热源施加 1 W 阶跃，再用 ERA 拟合较小的状态空间模型：

$ \begin{aligned}
x_{k+1}&=Ax_k+Bp_k+b,\\
T_k&=Cx_k+Dp_k+d.
\end{aligned} $

这里 p 是各热源的功率，x 是压缩后的热状态，T 是输出温度。x 的每个分量不必对应一个真实网格温度；这一式的输出矩阵 C，也不要和前式节点热容混淆。实验中的降阶模型有 224 个状态，每 10 ms 更新。

**④ 把温度反馈成服务变化。** 若未节流时服务时间为 s，当前服务比例 q 用百万分之一表示：

$ s_T=\left\lceil\frac{s\times10^6}{q}\right\rceil $

例如 q 为一百万，服务时间不变；q 为五十万，服务时间约变成两倍。这个例子只解释公式，不是论文实测的节流比例。

| 状态 | 对请求的影响 |
| --- | --- |
| Normal | 使用完整服务比例 |
| Light | 按配置降低服务比例，单次服务时间增长 |
| Severe | 暂停新的队列预留，先前已经接受的请求仍按原服务排空 |
| Shutdown | 返回明确的链路关闭终止状态 |


+ **不能重复算：** 同一次服务只施加一次温度缩放，避免主机和设备各放大一次。
+ **不能追溯卡住旧请求：** 请求在队列预留前获取状态快照，后续进入 Severe 也不能把已接收请求永久悬置。
+ **状态要成套读取：** 温度、模式和服务比例带版本保护，避免设备读到一半旧、一半新的状态。温度数据缺失、过期或来源出错时终止热运行，不一直沿用最后一次温度。

### 7. D4：保持、刷新和磨损也要变成应用付出的时间
+ **NAND本身特性会产生额外写入：** 应用虽然主要读取权重，但 NAND 的数据保持时间有限。为保留数据，设备可能需要把旧数据读出并重写；大量读取还会累积读干扰，因此不能认为只读负载没有内部写入。
+ **温度影响保持期限：** 原文使用 Arrhenius 模型：

$ L(T)=L_{\mathrm{ref}}\exp\left[\frac{E_{a,r}}{k_B}\left(\frac1T-\frac1{T_{\mathrm{ref}}}\right)\right] $

T 必须用开尔文。温度高于参考温度时，括号内为负，保持时间 L 缩短，刷新可能更频繁。它描述数据还能保持多久，并不等于整个器件还能使用多久。

+ **累计损伤：** 温度随时间变化，按下面的式子累计保持损伤：

$ D\leftarrow D+a_t\frac{\Delta t}{L(T)} $

其中 $ a_t $ 为论文披露的可靠性时间加速系数，用于让验证在可接受时间内完成。达到损伤阈值或读干扰上限后，块获得刷新资格。

+ **刷新怎么执行：** 按确定顺序生成页对齐的“读出—重写”请求，进入与前台访问相同的 MQSim 队列，实际占用介质服务。某裸片正服务应用读取时，刷新不会在这个裸片上同时执行。
+ **怎样记录磨损：** 只有一个块对应的所有刷新读写都成功，才提交一次编程/擦除计数，并清零相关损伤、干扰计数。失败就保留状态，后续可以重试，不能提前宣布刷新成功。
+ **为什么单独记请求：** 后台刷新与应用请求使用不同标识空间，刷新完成不能错误地唤醒应用的票据。发布给设备的相对字节债务用于表达还要支付的刷新工作，空闲期间本来能排空的部分另行扣除。

这一段的主线是：**温度升高 → 保持期限缩短 → 刷新增加 → 与应用争用带宽并消耗耐久性 → 后续访存更慢**。关键在于把设备内部变化传回真实执行，而不仅输出一个离线寿命数。

原文还用失效风险模型表达温度轨迹的影响：

$ H(E_a)=\sum_i\frac{\Delta t_i}{M_{\mathrm{ref}}}\exp\left[\frac{E_a}{k_B}\left(\frac1{T_{\mathrm{ref}}}-\frac1{T_i}\right)\right],\qquad P_{\mathrm{failure}}=1-e^{-H} $

这里 $ M_{\mathrm{ref}} $ 为参考条件下的寿命时间尺度；器件失效激活能与前面数据保持激活能是分开的参数。输出的是给定参数下的模型结果，不能当作测出了真实 HBF 的使用寿命。原文保持模型的 1.04 eV 参考值来自特定磨损条件的 3D NAND，换一种介质或磨损状态，需要重新检查。

### 8. D5：Capacity
+ **timing mode：** 保留数据原来的地址，重点改变指定访问的服务时间。
+ **capacity mode：** 用一块大小受限的显存页框缓存，加上主机稀疏后备文件。后备文件保存真实字节，显存只放当前换入的部分页面。
+ **命中：** 需要的页面已经在页框中，可以直接访问已有数据。
+ **缺页：** 向主机服务请求页面，执行相应介质模型服务，把字节复制到显存页框，再供 GPU 使用。
+ **脏页驱逐：** 若页面被修改，淘汰时必须把正确字节写回后备存储；不能只更新“这页已经写回”的记录。
+ **验证标准：** 换入、修改、驱逐、再次读回之后，校验和应与基线一致。一次介质请求成功，并不足以证明实际数据正确。

### 9. D6：Speculative Prefetcher
+ **为什么需要预测：** 稠密模型的权重读取顺序相对固定；MoE 的专家选择要等前面计算给出路由结果，提前量更难保证。
+ **默认策略：** 已服务某个缺页后，预取其后连续的页面；也提供接口让用户换成自己的策略。
+ **合成负载：** 每专家 8 页，缓存 256 个页框，共 1,033 个不同页面。

### 1. 实验平台
+ **GPU：** RTX PRO 6000 Blackwell 服务器版。
+ **模型与框架：** 用 vLLM v0.15.1 运行 Qwen3-30B-A3B，模拟器使用 CUDA 13.0 构建。
+ **实际存储：** 这张 GPU 使用 GDDR7 显存，通过页缓存支撑文中逻辑上的快速存储层；Dell CD8P SSD 用于已有闪存与主机分页路径的参考测量。
+ **HBF 参数：** HBF 硬件尚不可用，因此 HBF 服务由模拟器提供，配置约束取自 OCP 规范。

这里先分清两种结果：**GPU 上的模型执行是真实发生的；HBF 服务和封装温度则按给定配置建模。** 后面每组实验分别验证其中一部分。

### 2. EQ1：模拟器是否保留了正确执行，延迟是否加得准确
**① 先看完整模型能不能运行。**

+ **设置：** 输入 32 个词元，随机种子为 0，要求输出 8 个词元。
+ **结果：** 加载耗时 60.988 s，生成耗时 44.469 s，最终产生要求的 8 个输出并正常退出。另一个 llama.cpp 下的 TinyLlama 测试承受了十次 50 ms 的注入。
+ **说明：** 作者先验证加入 HBFSim 后，真实模型仍能走完加载、prefill 和 decode 流程。这些耗时包含实际执行与模拟路径成本，原文没有把它们作为未来 HBF 推理速度的预测。

**② 再看结果、地址归属和同步有没有出错。**

| 检查 | 原文结果 | 怎样理解 |
| --- | --- | --- |
| 普通访存与 TMA | 共 42 项检查，涉及 7 个可启动 TMA 模板 | 检查实际值、访问地址和同步行为是否保留 |
| HBM/HBF 归属 | 覆盖注册区间内外、混合边界与屏障依赖 | 应由 HBF 模拟的部分要计入服务，其余部分保留原生语义 |
| 超过缓存容量的访问 | 用 2 GiB 页框缓存访问 110 GiB 逻辑范围 | 验证小缓存可以支撑更大逻辑地址空间 |
| 数据一致性 | 已触及首尾区域的 128 个校验和与基线相同 | 验证被检查区域在换入换出后仍返回正确字节 |


这几项一起支持“声明覆盖内的功能正确性”。仅仅生成了相同输出，还不足以说明每个应模拟的访问都已被正确计时。

**③ 最后看加进去的延迟是否符合要求，见图 2。**

![](https://cdn.nlark.com/yuque/0/2026/png/40624596/1792725586619-7e0ce9e0-2607-4d49-b7e7-73f177c6b12d.png)_原论文图 2：延迟注入保真度，三个面板分别看增量误差、误差分布和延迟恢复比例。_

+ **实验设置：** 搬运 256 B 或 8,192 B 数据，每种大小都配置三个工作量 W0/W1/W2，共六种配置。W0 无额外整数循环，另外两档提供大约高于原生传输成本 10 μs、30 μs 的独立计算。每种配置做 36 对测量。

图 2(c) 可以这样理解：一次异步传输发生时，GPU 还有其他工作。如果加进去的延迟还没有成为决定最终耗时的那一项，最终测得时间就未必跟着增加。原文的参考模型取三项中的最大值，只有一项包含注入延迟，因此选择两个足够大的延迟来做差。

### 3. EQ2：同一封装中的热量会怎样影响 HBF
这一组包含三类证据：给定配置下的长期服务、封装热模型预测，以及现有 GPU 的测量参考。把它们分别读，就不会把不同温度、功耗数字混在一起。

**① 长时间运行时，有没有出现 HBF 热节流。**

+ **模型设置：** 一个 8 层 HBF 堆栈、16 个主机通道，采用第一速度等级的 384 GB/s 读取目标，每 10 ms 更新热状态。模型假定 ECC 不会先卡住额定带宽。
+ **功耗输入：** 5 W 空闲功率，加上每读取一字节的能量；在 384 GB/s 下，HBF 读取功率为 37.256 W。
+ **控制策略：** 比较不节流基线、两种迟滞设置、固定准入上限、比例积分控制，共五种策略。

| 运行时长 | 各策略在第 30–60 s 窗口的服务带宽 | 运行中的热状态 |
| --- | --- | --- |
| 600 s，即 10 分钟 | 384.0 GB/s | 没有节流，Severe 与 Shutdown 阈值以上的驻留时间均为零 |
| 3,600 s，即 1 小时 | 384.0 GB/s | 同上 |
| 86,400 s，即 24 小时 | 384.0 GB/s | 同上 |


原文报告峰值温度为 79.8 ℃，与热拟合预测相差不超过约 0.00003 K。它支持的结果是：**在这组模型配置下，384 GB/s 的目标服务没有因过热而降速。** 因为几种策略都没有触发节流，这组实验也没有显示某种策略比其他策略更优。

**② 如果继续提高封装中的热负载，谁先达到自己的温度上限，见图 3。**

### 4. EQ3：增加 HBF 后，容量与 MoE 需求怎样变化
这一组先用图 5 算“能放多少数据”，再用图 6 看“同一批请求会产生多少不同的专家需求”。

**① 图 5(a)：同一面积预算下，总容量能增加多少。**

<!-- 这是一张图片，ocr 内容为： -->
![](https://cdn.nlark.com/yuque/0/2026/png/40624596/1792725586849-c7fe3235-9b55-4b41-a062-25f2d4b80fdd.png)_原论文图 5：左图统计两层存储的总容量，右图统计特定放置前提下 HBM 中能驻留的 KV 容量。_

+ **共同条件：** 存储布局面积预算为 861.1 mm²，每个 HBM 堆栈按 36 GiB，每个 HBF 单元按 512 GiB。
+ **比较配置：** 下表分别列出全内存、中等闪存占比和较高闪存占比三种方案。

| 配置 | HBM 容量 | HBF 容量 | 总容量 | 使用面积 |
| --- | --- | --- | --- | --- |
| A：6 HBM | 216 GiB | 0 | 216 GiB | 861.1 mm² |
| B：3 HBM＋2 HBF | 108 GiB | 1,024 GiB | 1,132 GiB | 837.7 mm² |
| C：1 HBM＋3 HBF | 36 GiB | 1,536 GiB | 1,572 GiB | 754.2 mm² |


左图中灰色 HBM 部分逐渐减少，紫色 HBF 部分增加，最终让总容量从 216 GiB 增加到 1,572 GiB。B 虽有剩余面积，但其形状是约 1.94 mm 宽的窄条，放不下额外器件。

**② 图 5(b)：为什么总容量增加，能放在 HBM 的 KV 却减少。**

右图有一个明确前提：**完整的 54 GiB 专家权重先常驻 HBM，剩余 HBM 才用于 KV。**

+ **全内存方案：** 快速层有 216 GiB，放完专家和其他预留后，还能保留约 172 万词元的 KV。
+ **配置 B：** HBM 减少到 108 GiB，但要常驻的专家权重仍是同一套，因此留给 KV 的空间下降，只剩约 54 万词元。
+ **配置 C：** HBM 只有 36 GiB，连完整专家集合都放不下，已经不满足右图的前提，所以图中用短斜纹标记表示。

C 的容量可以按原文逐项算：

| 36 GiB HBM 中先扣除的内容 | 大小 |
| --- | --- |
| 固定驻留的非专家权重 | 2.8705 GiB |
| 工作区与安全预留 | 2.0000 GiB |
| 元数据 | 0.0010 GiB |
| HBF 传输暂存区 | 0.1406 GiB |
| 合计 | 约 5.0121 GiB |


于是 C 能留给专家的空间约为 **36−5.0121＝30.9879 GiB**，仅覆盖 54 GiB 专家集合的 57.4%。即使完全不放 KV，也无法让专家全部常驻。按同一预留，所需 HBM 至少约为 **54＋5.0121＝59.012 GiB**。

因此，图 5 的结论可以直接对应两个指标：**增加 HBF 能提高总容量，但减少 HBM 会压缩快速层里常驻权重和 KV 的空间。** C 的标记没有给出 KV 数值；它表达的是“完整专家集合无法常驻 HBM”，这套配置仍可以研究换页等其他运行方式。

这里的 172 万与 54 万是多请求可以共同占用的常驻 KV 总量。面积预算、36 GiB 示例容量以及工作区等预留是本组比较条件，二维布局结果也尚未验证走线、供电和制造可行性。

**③ 图 6：批量增大后，去重专家需求增加多少。**

<!-- 这是一张图片，ocr 内容为： -->
![](https://cdn.nlark.com/yuque/0/2026/png/40624596/1792725586949-0f255442-388b-460e-a99a-f130943d58f5.png)_原论文图 6：三种批量下的专家需求，均以批量 1 为基准；两条坐标轴采用对数刻度。_

+ **设置：** 捕获 Qwen3-30B-A3B 的路由轨迹，模型有 48 个专家层，每层 128 个专家，每个词元选择其中 8 个。测量批量 1、8、16。
+ **灰色虚线：** 路由决策次数随批量线性增加，作为没有复用时的参考。
+ **蓝色实线：** 把共享需求去重后，实际记录了多少需求事件。

| 批量大小 | 路由决策次数相对批量 1 | 去重需求事件相对批量 1 |
| --- | --- | --- |
| 1 | 1 倍 | 1.000 倍 |
| 8 | 8 倍 | 2.487 倍 |
| 16 | 16 倍 | 3.584 倍 |


例如，批量从 1 增加到 8，路由选择需要做八倍，但不同词元会选择重合的专家需求。去重后，共享部分只记一次，所以需求事件只增加到 2.487 倍。批量 16 时，同样的现象让去重需求只增加到 3.584 倍。

这说明**批量内存在专家需求复用，去重需求的增长慢于路由次数的增长**。权重有共享机会，各词元自己的计算仍然要完成。图中统计的是需求事件，实际介质读取字节、缓存命中和最终执行时间还取决于后续的数据管理；原文没有通过这张图测量预取加速比。

**EQ3 得到的结果：** HBM/HBF 配比决定“总容量”与“快速层常驻空间”的取舍；同时，MoE 批量内共享使专家需求不按请求数量等比例增加。这两项结果一起说明，设计 HBF 系统时需要同时考虑容量分配和实际需求复用。［原文 6.4，PDF 第 11–12 页］

### 5. 这部分实验应记住的三个结果
| 问题 | 按原文得到的结果 |
| --- | --- |
| 执行与延迟注入是否正确 | 完成真实模型执行，所测功能与同步检查保持正确；较大注入延迟之差可准确交付 |
| 热会不会先卡住 HBF | 在本文所测 384 GB/s 运行点没有节流；提高外部热负载后，当前模型里先到温度上限的是计算芯片 |
| 更多 HBF 是否一定带来更多可用快速容量 | 总容量增加，但 HBM 常驻 KV 空间可能减少；MoE 批量又会通过需求复用改变数据访问压力 |


本节依据本地原文第 6.1–6.4 节、PDF 第 9–12 页整理。图 2–6 均为原图；文中“为什么这样比较”的说明紧跟相应实验设置，数值按原文保留。
