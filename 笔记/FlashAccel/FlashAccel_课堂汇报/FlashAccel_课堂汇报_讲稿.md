建议总讲述时间：约 13 分钟，预留约 2 分钟用于停顿、临场补充和切换设备。

- 教室投屏建议使用 16:9，并提前确认论文图中的英文坐标是否清晰。

## 逐页讲稿

### 1. 封面（0.4 分钟）

FlashAccel 面向数据中心高吞吐 LLM 推理。它的核心问题不是“能否把模型放进 Flash”，而是“如何让 HBF 的容量优势真正变成吞吐量”。

转场：先看 HBM 容量如何直接限制 batch 和 KV 复用。

### 2. HBM 容量瓶颈（1.1 分钟）

- Qwen3-32B 的 FP16 权重约占 64GB；80GB H100 只剩约 16GB。
- 8K 上下文下，每个请求约需 2GB KV Cache，因此理论 batch 上限约为 8，实际还需给中间结果留空间。
- 小 batch 降低 decode 的算术强度；KV 被驱逐又会让多轮会话重复执行 prefill。

转场：HBF 提供大容量和高峰值带宽，但它本身有三个关键问题。

### 3. HBF 的三个挑战（1.1 分钟）

- 延迟：HBF 读取约 4μs，HBM 约 100ns，相差约 40 倍。
- 并行度：单 plane 读取 4KB/4μs，约 1GB/s；匹配 4.8TB/s 需要约 4,916 个 plane 并行。
- 偏斜：活跃请求动态变化，KV Cache 在 plane 间失衡；论文模型中最大 plane load 可高出平均值 52%。

结论：容量不等于吞吐。

### 4. 三层协同设计（0.8 分钟）

- 架构层：在 plane 和 base die 中加入 SRAM，做双缓冲预取。
- 数据布局层：为权重与 KV Cache 设计不同布局。
- 系统层：提供持久化对象、统一虚拟地址和专用接口。

资源分工：HBF 存权重和大部分 KV；HBM 存低延迟更新数据；SRAM 存下一块即将计算的数据。

### 5. 硬件集成（1.1 分钟）

- CLI 用 HBF 替换 6 个 HBM stack 中的 5 个，保留 1 个 HBM；成本更低，但总带宽比 CSI 少 16.7%。
- CSI 通过 HBM base die 级联 HBF，保留更多 HBM 容量与带宽。
- 每个 HBF stack 含 8 个 Flash die，每 die 96 个 plane，SRAM 总容量约 32MB。

转场：硬件只提供并行资源，权重布局决定这些 plane 能否同时工作。

### 6. 静态权重布局（1.0 分钟）

- A 表示算子 A 的全部静态模型权重。
- A0、A1、A2 是权重被切成 Flash page 大小之后的不同数据块，不是算子的性能权重或重要性分数。
- 模型计算图固定，因此可以离线获得算子执行顺序；权重按照这个顺序跨 channel 和 plane 轮转放置。
- 目标是降低最大 plane load，因为总体读取时间由最忙的 plane 决定。

### 7. KV Cache 动态均衡（1.3 分钟）

1. 把新 KV 尽量聚合为完整 hyper page 后写入 HBF。
2. 将超过平均负载的 page 选择性卸载到 HBM，避免在 HBF 内重新搬运和写入。
3. 按 hyper page 读取 HBF，并和 HBM 中的 KV 一起计算。
4. 本轮新生成 KV 先缓存在 HBM。
5. 形成完整块后再批量追加写回 HBF。

论文选择 256KB KV block，在 plane 偏斜、HBM 压力和内部碎片之间折中。

### 8. 存储管理与编程接口（1.0 分钟）

- 权重是只读对象，KV Cache 是 append-only 对象，因此无需通用 FTL 的完整更新语义。
- NandMmap 映射权重；GroupMmap、GroupArrange 和 GroupWrite 管理活跃请求的 KV。
- 页表可以动态指向 HBF、HBM 或 SRAM，应用始终使用统一逻辑地址。

### 9. SRAM 预取（0.9 分钟）

- 大权重张量切成可放入 SRAM 的 tile。
- 运行时按计算图生成异步 prefetch queue，让下一块读取与当前块计算重叠。
- SramPrefetch 不强制阻塞；预取尚未完成的页面仍保留 HBF 映射，从而保证正确性。

### 10. 评估设置（0.8 分钟）

- 基线：DGX-H200，8×H200，每 GPU 141GB HBM、4.8TB/s。
- 模型：Qwen3-235B、Qwen3-Coder-480B、LLaMA3.1-405B、DeepSeek-V3。
- SLO：50ms 与 100ms；上下文配置为 8.11K/2.53K 和 15K/6K。
- 作者在 LLMCompass 和 ScaleSim 基础上加入 plane 粒度 NAND 模型。

提醒听众：这是模拟器评估，并非真实 FlashAccel 芯片。

### 11. 主要结果（1.1 分钟）

- 在 100ms decode-step SLO 下，8×CSI 的平均每 GPU 吞吐达到 8×H200 的 2.54 倍。
- 平均能效达到 1.93 倍；8×CLI 的平均吞吐为 2.04 倍。
- 收益不是因为 HBF 单次访问快于 HBM，而是因为更大的容量支持更大的 batch，提高 FFN 算术强度。

### 12. 消融与 KV 复用（1.0 分钟）

- 去掉预取，吞吐下降 55%；预取是隐藏 Flash 延迟的主导机制。
- 去掉权重布局和 KV 布局，吞吐分别下降 7% 和 15%。
- 8×CLI/CSI 能在论文使用的多轮交互轨迹中保留全部会话 KV，使需要重新计算的 token 最多减少 89%。

### 13. 批判性分析（0.9 分钟）

- 贡献：硬件、数据布局与系统软件形成完整闭环。
- 实证边界：结果主要来自事件驱动模拟器，没有 HBF-GPU 实机原型。
- 功耗与制造：Flash 读取能耗约为 HBM3e 的 2.7 倍/bit；CSI TDP 增加约 31%，建模面积增加约 23%。
- 工作负载依赖：收益偏向 memory-bound decode、长上下文和大 batch；严格 50ms SLO 下，CLI 在部分模型上可能落后基线。

建议评价：这是有说服力的架构可行性论证，但还不是可以直接采购部署的产品证明。

### 14. 总结与问答（0.5 分钟）

三点总结：

1. HBF 解决权重与 KV Cache 的容量瓶颈。
2. 权重/KV 布局恢复 plane 并行度，SRAM prefetch 隐藏访问延迟。
3. 持久化对象和统一地址空间使 HBF 成为 GPU 的一等资源。

结束语：容量只有配合布局和预取，才会真正变成吞吐。

## 可能被提问的问题

### A0、A1、A2 是什么？

它们是算子 A 的静态模型权重被切成 Flash page 大小后的不同数据块，不是操作的重要性分数。

### 为什么不直接把 HBF 当成 HBM 使用？

HBF 首访延迟更高，而且峰值带宽依赖数千 plane 并行；不做布局和预取，有效带宽会远低于峰值。

### 为什么把过载 plane 的 KV 移到 HBM？

HBM 读取延迟低，且选择性卸载可以降低最大 plane load；相比在 HBF 内重排，它避免了额外 Flash 写入。

### 2.54× 是否适用于所有场景？

不是。该数字是论文在 100ms decode-step SLO 下报告的平均结果；收益会受到模型、上下文长度、SLO、batch 和硬件配置影响。

### 最大局限是什么？

缺少真实 HBF-GPU 原型。器件能耗、热设计、制造成本、控制器开销以及模拟器准确性仍需要实机验证。
