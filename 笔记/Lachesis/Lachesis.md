# Lachesis

**论文：** Lachesis: Lifetime-Aware KV Cache Placement for Agent Serving across HBM and High-Bandwidth Flash

**作者：** Jaehoon Yang、Jeongmin Lee、Haneul Park、Seung Yul Lee、Nam Sung Kim、Jae W. Lee；首尔大学、KAIST、UIUC。

**一句话理解：** 利用 agent 编排程序提前知道的上下文失效边界，让短命 KV 优先留在 HBM 并及时释放，使同一份 HBM 容量反复吸收新写入，减少真正到达 HBF 的写入量。

**和当前技术路线的关系：** 对照“设计 KV 预取和生命周期感知管理算法延长 HBF 寿命”，本文与**生命周期感知管理、减少 HBF 写入、延长设备寿命**高度相关，应作为直接相关工作和重要基线。**KV 预取不是它提出的机制**；如果后续只做“短命放 HBM、长命放 HBF”，会与本文核心贡献重合。更值得研究的是：预取缓冲与短命 KV 争用近端空间时，怎样联合决策，既满足延迟目标，又减少介质写入。下面将原文机制与面向自己课题的推导分别标明。

## 一、背景动机

### 1. Agent 场景里的 KV，为什么不能按一次请求管理

- **一次用户任务会调用很多次模型：** agent 在推理、工具调用、接收工具结果之后继续生成；一个 turn 内可以有多个 round，一个 session 又可以有多个 turn。
- **一次请求结束，KV 不一定失效：** 下一轮工具调用或下一条用户消息可能继续使用此前的上下文。多 agent 还同时保留主 agent 和多个子 agent 的上下文。
- **同一 session 内，不同 KV 的失效时机也不同：** 一部分推理上下文在轮次边界被剥离，子 agent 的工作上下文在返回结果后被丢弃，主 agent 的上下文则可能一直保留到整个任务结束。
- **因此需要比 request/session 更细的管理单位：** 作者把具有共同失效边界的一组上下文称为 **context segment，上下文段**；使这组上下文不再需要被读取的事件称为 **context boundary，上下文边界**。[原文 §1、§2.1、§3.1，PDF 第 1–5 页]

![Lachesis 的三类寿命差异与两条放置路径](images/figure-01.png)
_原论文图 1，PDF 第 2 页：左侧是三类上下文寿命差异，右侧是确定性路径和预测路径。_

- **左上：** 普通无状态请求的读取窗口通常随请求结束；agent 的读取窗口可能跨过很多次请求的 EOS。
- **左中两行：** 推理剥离和子 agent 返回提供了程序已知的失效边界。
- **左下：** 即使都属于 worker，不同任务的返回时间仍有很大差别，需要进一步排序。
- **右侧：** 能按语义确定类别的直接分层；同类 worker 再按预测寿命从短到长竞争 HBM。

### 2. HBF 的容量优势，需要和有限写寿命一起考虑

- **容量机会：** HBF 用 NAND 提供更大容量，模型权重和越来越大的 KV 有机会驻留在同一加速器附近。本文背景引用了每堆栈约为 HBM 16 倍的容量预期。
- **介质约束：** HBF 仍受有限编程/擦除次数约束。读取同一份已存在的 KV 与不断写入新的 KV，对耐久性预算的影响不同。
- **仅保存静态权重不够：** Agent 的容量压力很大程度来自在线生成、跨请求保留的 KV。如果所有生成 KV 都留在 HBM，HBF 无法充分缓解这部分压力。
- **本文切入点：** 在必须让一部分在线 KV 进入 HBF 的情况下，利用有限 HBM 尽可能多地吸收写流量。[原文 §2.2–§2.3，PDF 第 3–5 页]

**关键区别：** 本文要延长的是 **HBF 设备的预计使用寿命**，用于做决策的信号是 **KV 段从首次物化到失效的存活时间**。两种“寿命”不能混用。

### 3. 为什么让短命 KV 占 HBM，反而可能更省 HBF 写入

**HBM 的价值不仅是存下多少 GB，还包括这些空间在一段时间内能周转多少次。** 长命上下文即使暂时不读，也会一直占据容量；短命上下文失效后马上释放，同一块 HBM 可以接着容纳下一段数据。

用一个简化例子理解，**以下是辅助说明，不是原文实验**：有 1 GB HBM，一份需要一直保留的 1 GB 长命数据，以及十份依次到来、每份 1 GB、用完就失效的短命数据；忽略传输和其他开销。

| 放置方式 | 这段时间内 HBM 吸收的新写入 | 到达 HBF 的新写入 |
| --- | --- | --- |
| 长命数据先占满 HBM | 1 GB | 十份短命数据，共 10 GB |
| 长命数据进 HBF，HBM 依次容纳短命数据 | 10 GB | 一份长命数据，共 1 GB |

**这个例子解释的是周转机会：** 两种方式生成的数据总量相同，差别在于让哪一部分写入消耗闪存耐久性。实际收益还取决于段大小、并发度、失效时机和近端空间，不能据此认为“只按寿命排序”对任意工作负载都最优。[原文 §1、§2.3；例子为阅读推导]

### 4. 生命周期与读写比，回答的是不同问题

- **读写比问：** 这段 KV 写入后，被读取了多少次，是否值得付出写入代价。
- **生命周期问：** 这段 KV 要占着近端空间多久，什么时候可以释放并让出空间。
- **主 agent 的等待就是典型差别：** 子 agent 在工作时，主 agent 上下文可能长时间不读，但仍必须保留。它的寿命很长，读写比却未必比 worker 高很多。
- **本文的判断：** 在 agent 工作负载中，仅用输出长度或读写比代理生命周期，会漏掉工具等待、用户等待和任务结构带来的容量占用。[原文 §2.3、§3.4–§3.5，PDF 第 4–7 页]

## 二、设计方案

### 1. 先找出三个能区分上下文寿命的维度

| 维度 | 短命的一侧 | 长命的一侧 | 写入前可用的信号 | 放置原则 |
| --- | --- | --- | --- | --- |
| 时间维度 temporal | 当前 turn 内含推理的上下文段 | 剥离推理后跨 turn 保留的上下文段 | 编排程序的推理剥离规则、turn 边界 | 前者优先 HBM，后者 HBF |
| 结构维度 structural | 子 agent 的工作上下文 | 主 agent 的任务上下文 | spawn、return、session end | reviewer 优先 HBM；worker 再排序；主 agent 放 HBF |
| worker 间 inter-worker | 较早返回的 worker 段 | 较晚返回的 worker 段 | spawn 时的指令、上下文、工具列表和任务位置 | 预测寿命较短者优先 HBM，其余 HBF |

**短命和长命是各维度内的相对关系。** 论文没有设一个跨所有 agent、所有负载通用的“超过几秒就是长命”的阈值。前两类是语义类别可提前确定，第三类是相对次序可以预测；不能理解成每段 KV 的精确死亡时刻都已知。[原文表 1、§3.1、§4，PDF 第 4–9 页]

### 2. 时间维度：推理剥离让大量 KV 只活一个 turn

![时间维度的寿命分布和新增 KV 规模](images/figure-04.png)
_原论文图 4，PDF 第 5 页：上排比较标准化生命周期，下排比较每个 turn 新物化的 KV token 数。_

- **reasoning-laden：** 在当前 turn 的多次工具交互中持续使用的含推理上下文段。
- **reasoning-stripped：** 边界到来、推理被剥离后，保留给后续 turn 的上下文段。
- **观察到的差异：** 后者的生命周期中位数是前者的 **7.6–17.2 倍**；短命的含推理上下文段却占一个 turn 新写入 token 的 **66–83%**。
- **曲线怎么读：** 上排横轴是对数尺度的标准化秒数，曲线越向右表示活得越久；CDF 按段计数，不是按 KV 字节加权。下排是 token 规模分布，不能用上排曲线的间距直接推算写入百分比。
- **机制：** 含推理段在 HBM 中生成和使用；编排程序报告边界后释放。剥离后需要继续使用的段，按长命类别物化到 HBF。[原文 §3.3、§4，PDF 第 6、8 页]

**实现时特别注意：** 这两类是按未来复用关系划分的上下文段，不能直接简化成“所有 thinking token 放 HBM、所有答案 token 原样搬到 HBF”。原文明确把重新物化视为一个新段，并单独计入它的写入量；它没有给出一套剥离推理后直接复用任意旧位置 KV 的算法。[原文 §3.2、附录 B，PDF 第 5、14–15 页]

### 3. 结构维度：子 agent 用完就释放，主 agent 保留任务状态

![主 agent、worker 和 reviewer 的生命周期与读写比](images/figure-05.png)
_原论文图 5，PDF 第 6 页：上排比较生命周期，下排比较每写一个 token 对应的解码读取量。_

- **lead agent：** 保存系统提示、用户目标、子任务派发信息以及返回结果，直到 session 结束。
- **worker：** 负责具体子任务，在独立上下文里多次调用工具；任务返回后，工作上下文失效。
- **reviewer：** 接收已完成 worker 的轨迹并给出审查，原文配置下不再继续派发任务，通常比 worker 更短命。
- **寿命差异：** 主 agent 段的生命周期中位数是 worker 的 **4.0–6.1 倍**，是 reviewer 的 **4.7–38.3 倍**。
- **读写比解释不了全部差异：** 主 agent 生命周期中有 **71–88%** 在等待且没有读取。图 5 下排里主 agent 与 worker 的读写比分布仍明显重叠。[原文 §3.4，PDF 第 6–7 页]

**放置结果：** 主 agent 段直接放 HBF；reviewer 获得 HBM 优先权；worker 是否进入 HBM，还要看预测路径和剩余容量。子 agent 返回时释放的是它不再使用的段，返回给主 agent 的结果仍属于后续需要保留的上下文。

**这对自己的课题很有价值：** “当前不热”和“已经死亡”必须区分。等待中的主 agent 段可以降低近端驻留优先级；只有编排程序确认失效的段，才能真正释放。

### 4. worker 间再排序：在 spawn 时预测谁会更早结束

![同一 worker 类别内部的寿命与写入规模差异](images/figure-06.png)
_原论文图 6，PDF 第 7 页：左侧是各任务的 worker 生命周期分布，右侧是生命周期与新写入 token 数的关系。_

- **只认“子 agent”还不够：** 同一 benchmark 内，worker 生命周期的 p90/p10 为 **3.7–23.6 倍**，写入规模的 p90/p10 为 **2.8–22.5 倍**。
- **写得多不完全等于活得久：** 二者 Kendall's τ 为 **0.51–0.72**。轮数会同时增加生成量和生命周期，工具等待则只延长时间，不直接增加 token。
- **预测时机：** worker 被创建时，读取 spawn record，不需要先观察它后续执行。
- **输入特征：** 指令和上下文长度、工具的指示特征、session 内位置，以及文本的哈希词袋特征。
- **预测器：** 岭回归训练的线性模型，五种 structural benchmark 共用一个模型。放置只消费预测值诱导出的**排序**，不把预测秒数当作精确完成时间。[原文 §3.5，PDF 第 7–8 页]

![spawn 时的寿命预测与短命 worker 选择效果](images/figure-07.png)
_原论文图 7，PDF 第 7 页：左侧按预测次序分四组，右侧检查选出的 worker 与真实短命集合的关系。_

- **排序质量：** Kendall's τ 为 **0.53**。这是排序相关性，不能写成“预测准确率 53%”。
- **交叉验证：** 按 session 分组做五折验证，同一 session 的 worker 不会同时进入训练和验证。
- **选最短的 10%：** 所选集合中 **62.8%** 属于真实最短寿命的 10%，且没有选中真实最长寿命的 10%。不能解释成“任意容量下都能找对 62.8%”。
- **实际准入：** 对节点服务的各 session 的 worker 按预测寿命排序，先为 reviewer 留出 HBM，再接纳容量容许的前 k 个 worker。k 随 HBM 空闲容量变化，是容量截断结果。[原文 §3.5、§4，PDF 第 7–9 页]

**原文没有展开的部分：** reviewer 要预留多少字节、如何从剩余字节预算精确换算 k、worker 后续增长超出预算怎么办，以及新 worker 到来后是否重排已有驻留段，都没有给出完整伪代码。不能把本文补写成已经实现了在线迁移、精确大小预测或误预测纠正机制。

### 5. 系统概览：编排程序提供语义，放置层决定内存层，引擎执行分配

![Lachesis 总体架构与分配释放接口](images/figure-08.png)
_原论文图 8，PDF 第 8 页：Lachesis 位于 agent harness 和 serving engine 之间。_

**从上往下看：**

- **Agent harness，编排程序：** 告诉 Lachesis 每个请求延长哪个段、worker 的 spawn record，以及哪些上下文边界已经到达。它负责定义任务语义，Lachesis 不自行改变 agent 的推理或丢弃规则。
- **两条决策路径：** 确定性路径处理含推理/剥离推理、主 agent/reviewer 等类别；预测路径处理 worker 类别内部的寿命排序。
- **Segment table：** 每个活跃段一行，记录 segment id、类别、失效边界和已经分配的 KV block id。段元数据随活跃段增长，保存 block id 的开销还随活跃块数增长。
- **Serving engine：** 维护 HBM、HBF 两个空闲块列表，按上层指定的层分配。引擎接口自身不需要理解 turn、推理内容或子 agent 角色。
- **管理范围：** Lachesis 改变的是 KV 放置，模型权重沿用既有只读映射，activation 仍放在 HBM；它没有重新设计整套权重与中间结果布局。

一次段的生命周期可以按四步记：

1. **建立语义与类别：** 编排程序报告段标识、类型和边界；worker 创建时另外计算寿命排序。
2. **写入前决定层：** 长命类别放 HBF，短命类别和排名靠前的 worker 优先 HBM。分配 HBM 块但列表为空时，退回 HBF。
3. **分配并登记：** 每分配一个块，就把 block id 加入该段的表项，后续请求继续扩展相应段。
4. **边界到达即释放：** 编排程序确认段失效后，Lachesis 释放该段的块，并删除表项，空间可以服务下一批 KV。[原文 §4，PDF 第 8–9 页]

两个面向引擎的接口分别是：

| 接口 | 做什么 | 与生命周期的关系 |
| --- | --- | --- |
| `alloc(tier)` | 从指定内存层分配一个 KV block | 放置层已决定 HBM/HBF，引擎按层分配 |
| `free([block ids])` | 把一组块归还各自的空闲列表 | 由语义边界触发，无需等 LRU 根据长时间不访问再猜测 |

**“两个接口”是对 serving engine 的接口数量。** 系统仍依赖编排程序额外提供段标识和失效事件，不能据此说它只改两个函数就能透明适配任何 agent 框架。

**逻辑释放与 NAND 擦除也要分开：** `free` 归还的是引擎管理的 KV 块；真实 HBF 怎样把失效页组织成可擦除块、要搬移多少有效数据，仍需要介质管理策略。本文用接近 1 的写放大作简化，没有提出完整的生命周期分组垃圾回收算法。

### 6. 它怎样计量生命周期，怎样计入写带宽

**标准化生命周期是工作负载分析指标，不是设备损坏时间。** 为减少服务器负载、batching 和排队的影响，原文使用固定参考时钟：

**原文式（1），PDF 第 5–6 页：**

$$
T_{\mathrm{norm}}(s)
=G_{\mathrm{dec}}(s)\,\mathrm{TPOT}_{\mathrm{ref}}
+N_{\mathrm{obs}}(s)\,\mathrm{TTFT}_{\mathrm{ref}}
+\Lambda_{\mathrm{tool}}(s)+\Lambda_{\mathrm{user}}(s).
$$

- **解码项：** 在段 s 存活期间计入的解码 token 数，乘参考每 token 时间 **0.2 s**。主 agent 等待子 agent 执行的时间也会延长主 agent 段的存活窗口。
- **Observation 项：** 工具结果进入上下文，触发局部 prefill；每次 observation 计参考 TTFT **1.0 s**。
- **等待项：** 加上工具执行与用户回复的等待；这些来自模型采样，不是所有 benchmark 都记录了真实等待时间。
- **计量边界：** 初始 prefill 的 token 计入写入量，但初始 prefill 时间不计入该生命周期；读写比只统计 decode 读取，不包含 observation 的局部 prefill 读取。

**0.2 s/1.0 s 是分析寿命用的参考参数。** 后面性能实验的 60 ms/100 ms TPOT 和 2 s TTFT 是另一组 SLO，不能把两组数字混成同一配置。[原文 §3.2、§5.2、附录 B，PDF 第 5–6、9、14–15 页]

**HBF 写带宽怎样计时：** 模拟器把需要进 HBF 的 KV 跨 decoder layer 缓冲，在一个 decode step 结束时集中 flush，以 HBF 写带宽计算这次 flush 的时间。它降低小次写入的时序影响，但不等于按生命周期过滤数据，更不等于减少了同样字节数对应的 P/E 消耗。[原文 §5.1，PDF 第 9 页]

### 7. 和当前技术路线逐项对照

**这里的技术路线以你给出的截图为准：设计 KV 预取和生命周期感知管理算法，延长 HBF 寿命。以下是结合原文做的课题判断。**

| 路线中的问题 | Lachesis 已做什么 | 对自己方案的影响 |
| --- | --- | --- |
| 生命周期感知 | 从编排语义分段，结合 worker 寿命排序 | 直接相关，必须作为重要对照 |
| 减少 HBF 写入 | 短命段留 HBM，失效后立即回收，提升 HBM 周转 | 这一核心思路已被覆盖 |
| KV 预取 | 没有新预取算法；把延迟隐藏与平面均衡视为已有工作处理的问题 | 可以继续研究，但要和已有预取机制比较 |
| 近端空间如何分配 | 给短命 KV 优先权，并为 reviewer 留空间 | 没有联合决定预取缓冲和短命驻留的份额 |
| NAND 物理管理 | 假设整块顺序写、低搬移开销，写放大固定为 1.02 | 物理布局、GC、刷新和误预测成本还需评估 |
| 温度和持续运行 | 以平均写速率外推寿命 | 没有完整验证热限流、读干扰刷新对联合策略的反馈 |

**它适合做自己方案的“生命周期放置基线”。** 可借鉴的信息来源是 agent 语义边界，而不只是 LRU 热度。若自己的工作负载是一般在线请求、跨请求共享前缀或无法提供失效事件的系统，则还要说明生命周期信号从哪里来，不能直接假设能拿到相同信息。

**和 FlashAccel 的关系：** FlashAccel 提供 HBF 数据布局、显式 SRAM 预取和按计算顺序调度等机制；Lachesis 决定在线生成的 KV 哪些进入 HBF、何时释放。二者分别提供了读取路径与语义放置的基础。直接把两者拼接，仍需证明联合决策本身产生了额外收益。[Lachesis §2.2、§6；FlashAccel §5、§6.2.3]

### 8. 可以怎样把自己的路线继续做具体

**以下是候选扩展与实验建议，不是 Lachesis 已实现的方法，也不代表已经确认的新颖性。**

**首先明确两类近端数据：** 一类是还没写入 HBF 的短命原生 KV，留在近端可以避免闪存写入；另一类是 HBF 已有 KV 的只读预取副本，作用是隐藏读取等待。二者占用同一份 HBM 时会发生直接竞争；预取到独立 SRAM 时也有容量、带宽和执行资源约束。

**一个值得检验的失败场景：** 大批预取副本占满 HBM，迫使即将死亡的原生 KV 溢出到 HBF。读取等待虽然减少，闪存新写入反而增加，设备寿命可能下降。解决这个冲突，比仅给预取器加一个固定提前量更贴近当前技术路线。

可以按以下几个环节形成联合机制：

1. **先决定哪些 KV 值得写入：** 利用真实边界和剩余寿命信息，让近端优先吸收将很快失效的数据；对必须溢出的段，显式考虑大小、未来读取和写预算。
2. **再决定何时预取：** 对已经驻留 HBF、确定即将使用的 KV 分块预取；随可用计算重叠窗口和缓冲空间调整提前量。全注意力下重点是读的时机、分块和流控；若只取部分 KV，则还需要独立的选择依据与精度验证。
3. **控制两类空间的竞争：** 限制预取副本不能挤掉收益更高的短命原生 KV；边界到达时取消无用预取，并回收缓冲。
4. **避免副本淘汰制造新写入：** 在保留 HBF 原副本且预取副本未修改的前提下，近端副本可以直接丢弃。它与尚未落盘的新 KV 不能使用相同的写回处理。

**判断延寿要看介质写入，而不只看预取命中率。** 便于理解的寿命预算关系为：

$$
L_{\mathrm{HBF}}\approx
\frac{C_{\mathrm{HBF}}\,N_{\mathrm{PE}}}
{A\,\dot W_{\mathrm{host}}}.
$$

这里 C 是对应 NAND 模式下的总容量，N 是可承受的 P/E 次数，A 是写放大，W 的变化率是进入 HBF 的逻辑写入字节率；若时间单位用秒，L 也为秒。**此式是根据寿命预算整理的说明式，原论文没有给它编号。** 若直接测得包含搬移、刷新等活动的介质写速率，分母就用该速率，不应再次乘 A。

**预取本身主要改变读取等待。** 它要帮助延寿，需要在相同服务量下减少不必要的 HBF 写入或放大，同时避免额外读取引起的能耗和刷新成本。仅把数据读得更早，不能直接宣称降低了 P/E。

## 三、实验结果

### 1. 实验设置与比较对象

| 项目 | 原文设置与口径 |
| --- | --- |
| 评估方法 | 真实 agent 轨迹驱动的两层内存和 serving engine 仿真，没有真实 HBF 芯片寿命实测 |
| 执行模型 | Frontier 提供调度、请求队列和 KV 管理；LLMSimulator 及既有 HBF 扩展提供算子、roofline 和内存带宽计时 |
| 系统位置 | Prefill/decode 分离部署的 decode 节点，评估模型使用 8 GPU，attention 用数据并行，专家用专家并行 |
| 执行轨迹采集 | 两种分析 regime 都使用 Gemma 4；时间维度用 Harbor，结构维度用 AOrchestra |
| 性能计时模型 | Llama-4-Maverick、Qwen3-235B-A22B；与采集轨迹时使用的 Gemma 4 区分 |
| 共置拓扑 | 8 个堆栈位置按 HBM/HBF 分为 1/7、2/6、3/5、4/4 |
| 级联拓扑 | H³ 的 8/8*，HBM 与 HBF 级联，不能当作总共只有 8 个堆栈的另一种比例 |
| 读取假设 | 两层具有相同读取带宽，写带宽不同；较长读取延迟的隐藏沿用既有工作假设 |
| SLO | TTFT 2 s；p99 TPOT 分 tight 60 ms 与 loose 100 ms；单 agent 只运行 tight |
| 耐久性假设 | SLC，100,000 次 P/E，每 HBF 堆栈 512 GB，写放大 1.02 |
| 寿命统计 | 稳态平均 KV 写入速率下外推，排除首次加载模型权重的那一次写入 |
| 基线 | HBM-first：有 HBM 空闲块就分配，否则 HBF；原文结果分析指出它主要在内存压力下回收 |

**轨迹组成：** 单 agent 为 τ³-bench 和 BFCLv4；多 agent 混合 AppWorld、DeepSearchQA、SWE-bench Verified、TerminalBench、WebArena。时间维度配置只激活推理剥离边界，结构维度配置只研究子 agent 返回边界；不是在每条轨迹里同时验证三种机制。附录表 3 记录了各语料规模，失败和超时 session 也未排除。[原文表 2、表 3、§5.1–§5.2、附录 A，PDF 第 4、9、14–15 页]

### 2. 多 agent：在相同拓扑内减少 HBF 写入，寿命提升

![多 agent 的 HBF 预计寿命](images/figure-09.png)
_原论文图 9，PDF 第 10 页：黑色为 HBM-first，斜线为仅确定性路径，黄色为完整 Lachesis；虚线为五年目标。_

- **上排/下排：** tight/loose SLO。两模型内部还分关闭 reviewer 和开启 reviewer，原文默认结果采用开启 reviewer 的轨迹。
- **横轴：** HBM/HBF 堆栈配置；8/8* 是单独的 H³ 级联拓扑。断开的柱子和标注数字说明其结果超出了普通纵轴范围。
- **共置配置下的相对收益：** tight SLO 延寿 **1.50–2.95 倍**，loose SLO 延寿 **1.19–1.89 倍**。
- **共置配置下的绝对寿命范围：** 正文汇总 Lachesis **3.3–9.3 年**，HBM-first **1.9–4.8 年**。这是包含不同 SLO 的范围；3.3 年不能拿来描述“tight 下全部超过五年”的那组结果。
- **五年结论的条件：** 多 agent 的 tight SLO 下，Lachesis 在所有测试拓扑、两个模型上都超过五年；loose SLO 放入更多并发 session 后，部分配置低于五年。[原文 §5.3，PDF 第 9–10 页]

**原因：** 并发越高，同一时刻活着的短命 KV 越多。若 HBM 容量不变，就越容易溢出到 HBF。寿命感知有收益，并不意味着在任意负载下都能达到五年目标。

### 3. 写入构成：收益来自 HBM 周转，不能只看驻留容量

![多 agent 的两层写入量与角色构成](images/figure-10.png)
_原论文图 10，PDF 第 10 页：Llama-4-Maverick、loose SLO；上排是 HBM 写入，下排是 HBF 写入，按整条轨迹总写入量归一化。_

- **纵轴含义：** 统计新写入字节的去向，不是某一时刻 HBM/HBF 的容量占用率。
- **HBM 吸收更多写入：** 原文报告，Lachesis 写入 HBM 的 KV 是 HBM-first 的 **8.2–19.5 倍**；HBM 吸收轨迹写入的比例为 **19–51%**，基线只有 **1–7%**。
- **主 agent 不再长期占近端空间：** 主 agent 段在写入时进入 HBF，短命子 agent 更容易进入 HBM 并及时周转。
- **总生成量没有减少：** 相同轨迹下，改变的是写入落到哪一层。部分长命段进入 HBF 的写入有所增加，但更多短命写入被 HBM 吸收，总 HBF 流量仍下降。[原文 §1、§5.3，PDF 第 3、10 页]

**为什么不是“短命数据也很快写完，所以写哪都一样”：** 对 HBF 来说，写一次后马上死亡，仍然花掉一次写入预算；对 HBM 来说，早点死亡意味着空间能早点用来接下一份新数据。

### 4. 消融：语义类别和 worker 排序各贡献一部分

| 对照 | 原文报告的收益 | 说明 |
| --- | --- | --- |
| 仅确定性路径 vs HBM-first | 1.11–2.00 倍寿命 | 利用段类别与边界已有收益 |
| 完整 Lachesis vs 仅确定性路径，有 reviewer | 再提升 1.33–1.54 倍 | worker 排序为更短命的 reviewer 保留了近端机会 |
| 完整 Lachesis vs 仅确定性路径，无 reviewer | 再提升 1.05–1.14 倍 | 只在 worker 内调整驻留对象，额外收益较小 |

**reviewer 的变化最直接：** 没有预测路径时，reviewer 自身写入中 **45–95%** 进入 HBF；完整 Lachesis 下为 **2–25%**。预测器虽然只排序 worker，却通过减少长命 worker 对 HBM 的占用，间接保护了 reviewer。[原文 §5.4、图 9–10，PDF 第 10–11 页]

**读数时注意：** 前两行是逐级比较的倍率，不能把各自的范围端点直接相乘，当作某个已观测配置的精确收益。

### 5. 单 agent：不需要 worker 预测，时间边界本身就能延寿

![单 agent 的 HBF 预计寿命](images/figure-11.png)
_原论文图 11，PDF 第 11 页：上排 τ³-bench，下排 BFCLv4；全部为 tight SLO，虚线为五年目标。_

- **四种共置配置：** Lachesis 寿命为 **4.6–12.2 年**，HBM-first 为 **2.1–6.4 年**，提升 **1.35–3.13 倍**。
- **只用确定性路径：** 这两条轨迹没有多 agent worker 排序，收益来自推理剥离带来的段级放置与回收。
- **仍有例外：** Lachesis 只有一个配置没到五年，图中对应 Qwen3-235B-A22B、BFCLv4、4/4；不能写成“所有单 agent 配置均超过五年”。
- **H³ 结果另算：** τ³-bench 的 H³ 柱子标出了 **16.5 年、17.4 年**。它们不在前面 4.6–12.2 年的共置配置范围内。[原文 §5.5、图 11，PDF 第 11 页]

![单 agent 的含推理段与剥离后段分别写入哪一层](images/figure-12.png)
_原论文图 12，PDF 第 11 页：Qwen3-235B-A22B、tight SLO；黑色为含推理段，斜线为剥离推理后保留的段。_

**这张图解释了收益来源：** HBM-first 的 HBM 写入比例很低；Lachesis 则把大批短命含推理段留在 HBM。容量达到足以覆盖活跃短命段的程度后，再扩大 HBM，吸收的写入不会继续按比例上升。

### 6. 更多 HBM，不一定让 HBF 活得更久

**共置配置存在两股相反作用：** 从 1/7 增加到 4/4，HBM 更多，但 HBF 堆栈从七个减成四个，系统的总 P/E 字节预算也随之下降。

- **HBM 还不够时：** 增加容量能减少短命 KV 溢出，少写入的收益可能超过少一个 HBF 堆栈的损失。
- **HBM 已够时：** 新增 HBM 不再吸收更多短命写入，但仍要减少 HBF 堆栈，总耐久预算降低，预计寿命反而下降。
- **原文例子：** BFCLv4 下，从一个 HBM 堆栈增加到四个，Lachesis 的预计寿命反而少 **30–31%**。
- **最优点会随负载移动：** 它取决于 HBM 相对于“同一时刻活跃短命 KV”的容量比例，不能用总数据集中短命 KV 的百分比代替。[原文 §5.3、§5.5，PDF 第 10–11 页]

**H³ 级联必须单独看：** 它保留 HBM 的同时不减 HBF 堆栈。多 agent tight SLO 下，Lachesis 相对该拓扑自身的 HBM-first 可达 **10.06–10.09 倍**，loose 下为 **2.53 倍**。这是不同硬件拓扑内的比较，不应与 1/7–4/4 的共置结果混成一个范围。[原文 §5.3，PDF 第 10 页]

**因此摘要的数字要带范围：** 摘要给出的 **1.19–3.13 倍、3.3–12.2 年**概括了前述共置配置的结果，未覆盖 H³ 中更大的寿命和倍率；原文正文另外报告了 H³ 结果。

### 7. 阅读时需要保留的条件

- **寿命是预算外推：** 假定持续 24×7 运行、稳态平均写流量、SLC 的 100,000 次 P/E 和固定 1.02 写放大，并非真实设备运行多年后的故障统计。不能直接套到 TLC 或其他容量、耐久性配置。
- **读路径已经比较有利：** 两层按相同读取带宽计时，HBF 读取延迟隐藏和平面均衡被放在本文范围之外。它没有验证一套新预取器，也没有单独证明真实 HBF 上全部访问延迟都能隐藏。
- **编排语义是前提：** 推理剥离、子任务返回等边界必须由实际框架提供。前两类知道的是终止规则，worker 知道的是预测次序，不是全部精确寿命。
- **比较包含多种变化：** 相对 HBM-first，Lachesis 同时改变初次放置和语义边界回收。论文没有单独列出“HBM-first 加同样即时回收”的强基线，因而不能把全部收益都归到初次放置上。
- **物理管理仍简化：** 接近单位的写放大依赖整块顺序写、少量 GC 和磨损均衡搬移。多寿命段混放、预测失误、刷新与读干扰可能改变真实介质写入。
- **可复现细节有限：** 原文未完整给出容量到 k 的映射、reviewer 预留策略、模型误差处理和具体请求率；也没有以完整吞吐/延迟曲线分离各策略在固定服务量下的差异。
- **性能结论要适度：** 本文主结果是给定 SLO 下的预计耐久性，不能据此写成“延迟零开销”或“吞吐提高若干倍”。线性预测器计算轻，并不等于整套系统已经完成实际部署开销测量。

### 8. 自己的课题应怎样设置对照与指标

**建议在同一硬件拓扑、同一工作负载和同一服务量下先比较，再补各策略的最大 SLO 吞吐。** 这样可以分清写入下降到底来自更好的管理，还是来自处理了更少请求。

| 对照组 | 要分离的问题 |
| --- | --- |
| HBM-first | 基础分配方式 |
| HBM-first + 相同语义边界即时释放 | 单看及时回收能贡献多少 |
| Lachesis 确定性路径 | 语义类别放置带来的变化 |
| 完整 Lachesis | worker 排序带来的额外变化 |
| 完整 Lachesis + 统一固定预取策略 | 判断直接组合已有机制的效果 |
| 自己的生命周期/预取联合策略 | 判断联合空间管理、提前量和写预算控制的额外收益 |

**核心指标需要同时报告：** HBF 逻辑写入与介质写入、写放大、预计寿命、p99 TTFT/TPOT、满足 SLO 的有效吞吐，以及近端容量占用。诊断联合机制时再看短命 KV 溢出字节、有效/无效预取字节、预取及时率、缓冲驻留时间和刷新流量。

**值得优先做的压力场景：** 并发增加使短命 KV 超过 HBM；工具等待变化导致寿命排序失准；预取提前量增大导致空间被占；长短命段在物理擦除块内混放导致写放大上升。分别画出性能和介质写入变化，才能判断“预取加生命周期管理”是否真正延长 HBF 寿命。

**对当前路线的判断：** Lachesis 的仿真表明，“利用 agent 语义改善 KV 放置、减少 HBF 写入”是有价值的方向，也已经占据了其中最直接的一块。自己的工作需要进一步回答：**当预取和短命 KV 共用有限近端资源时，怎样联合决策，才能在满足服务目标的同时降低介质写入。** 这是从该文继续推进的候选问题，仍需检索其他相关工作并用实验确认。
